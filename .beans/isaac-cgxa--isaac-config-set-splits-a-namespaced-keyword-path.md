Found 2026-09-19 on yopp: `isaac config set comms.gchat.gchat/allow-from …` and `… comms.gchat.gchat/spaces.spaces/AAQA….respond all` wrote `{:comms {:gchat {:gchat {:allow-from …, :spaces {:spaces {:AAQA… {:respond "all"}}}}}}}` — the / in a namespaced keyword is treated as a path separator — and `config validate` passed, so the stray map sat there silently while the real keys were untouched. Comm extra-schema keys are all namespaced (gchat/…, gmail/…, discord/…), so this affects every comm slot; the feature harness's config table step parses these paths correctly, the CLI does not.

Do: the path parser treats a segment containing / as a namespaced keyword (`gchat/allow-from` → :gchat/allow-from; `spaces/AAQA7rg5Uyc` → :spaces/AAQA7rg5Uyc). Escape hatch if a literal / in a key name is ever needed. Also: a set that would create a key the schema does not know inside a schema'd map (`:gchat` under comms.gchat) should be refused, not written — that is why this stayed invisible.

Scenarios (foundation features/config): set comms.x.x/field writes the namespaced key; set comms.x.x/map.ns/key.field writes nested namespaced keys; get reads them back; a set creating an unknown key under a schema'd map is refused.


## Worker checkpoint 1 (2026-09-21, scrapper@isaac-work-1)

Claimed; investigation complete, no code written yet (nothing to commit on the branch).

**Root cause confirmed.** `c3kit.apron.schema.path/parse` tokenizes on `[a-zA-Z_\-][a-zA-Z0-9_\-]*`, so `gchat/allow-from` becomes TWO `[:key …]` segments (`:gchat`, `:allow-from`) — the `/` is simply dropped by the regex. Three foundation call sites consume it: `src/isaac/config/mutate.clj:110` (parse-config-path — the set/unset writer), `src/isaac/config/schema/resolve.clj:25` and `:35` (schema-for-data-path — what CLI set consults for the value type). The schema side (`isaac.config.nav/path->spec`) splits only on `\.`, so it already treats `gchat/allow-from` as one segment — that asymmetry is exactly why the schema walk says "ok" while the writer splits it in two and `assoc-path` nests `{:gchat {:allow-from …}}`.

**Harness parity confirmed.** The feature-table step (`spec-support/src/isaac/foundation/fs_steps.clj:274-277 isaac-value-path`) does `(mapv keyword (str/split path #"\."))` — slash survives because `(keyword "gchat/allow-from")` → `:gchat/allow-from`. That's the "feature harness parses these correctly, the CLI does not" from the bean.

**Also confirmed while probing:** `path/data-at` (config get) has the same two-segment split, so get can't read a namespaced key back either.

**Plan (next):** TDD. Specs first in `spec/isaac/config/mutate_spec.clj` (and `nav_spec` already covers the nav side). The fix belongs in foundation's own path handling, not c3kit (a vendored mvn lib, 3.0.0): a foundation-side parse that treats a `.`-separated segment containing `/` as one namespaced-keyword segment, feeding BOTH `mutate/parse-config-path` and `schema/resolve` (plus `path/data-at` reads via the CLI get path). Escape hatch already exists in the grammar: `["quoted"]` string segments. Scenarios per the bean into `features/cli/config_resolution.feature`-style harness (need a feature file driving `isaac is run with "config set …"`; check which feature file is the right home).

**Resume from:** `src/isaac/config/mutate.clj:109` (`parse-config-path`), `src/isaac/config/schema/resolve.clj:25`,35; repro scripts at `/tmp/cgxa-repro*.clj` (bb -f).

**What changed (one commit, no src/spec production-code changes beyond what the rebase carried in from `2f75cef`/`a79a28e`):**

Investigated the "second grammar site" lead from the checkpoint above and it turned out to be a **misdiagnosis** -- `src/isaac/config/nav.clj`'s `advance-spec` needed **no code change**. `isaac.schema.dynamic/compose` (called by `isaac.config.schema-compose/effective-root-schema`, which both `nav.clj`'s CLI callers and `schema.resolve.clj` consume) already flattens a berth's `:dynamic-schema`-declared `:extra-schema` fields into the composed `:schema` map *before* `nav.clj` ever walks it -- so `advance-spec`'s existing `(get (:schema spec) (keyword seg))` lookup already finds `:helm/freq`/`:helm/outer` (or any other namespaced dynamic field) correctly, since `(keyword "helm/freq")` already yields the right qualified keyword. Verified this by instrumenting `advance-spec` with a temporary `println` and watching it resolve namespaced segments correctly against the real composed schema -- then reverted the instrumentation (nav.clj is untouched, `git diff eaae014..HEAD -- src/isaac/config/nav.clj` is empty).

The actual 2-of-4 redness was **entirely a test-fixture bug** in `features/cli/config_set_namespaced.feature`, four separate issues stacked on top of each other, each masking the next:

1. **Module id collision.** The fixture declared modules `:marigold.bridge` / `:marigold.longwave` at `/tmp/modules/...` -- but this repo already ships its own builtin fixtures at `modules/marigold.bridge/` and `modules/marigold.longwave/` (used elsewhere, e.g. `module_deps.feature`) with the *same ids*. Module discovery served the repo's real fixture instead of the feature's own `/tmp` declaration (confirmed by instrumenting `module-index-for-config`/`merge-dynamic-fields` and watching the discovered manifest carry the real fixture's `:helm/freq` message/validations plus an unrelated `:relay-station {}` entry that only the real fixture declares). The real fixture doesn't declare `:helm/outer` at all, which is what actually produced the "unrecognized segment: helm/outer" error the checkpoint attributed to `nav.clj`. Fixed by renaming the fixture ids to `:marigold.cgxa.bridge` / `:marigold.cgxa.longwave` (paths and namespaces to match) so they can never collide with `modules/*` again.
2. **Malformed manifest EDN.** The `:marigold.bridge/comm` berth manifest (Background) was missing one closing `}` -- `(clojure.edn/read-string ...)` threw `EOF while reading`. This existed on `2f75cef` already; it was invisible before because issue (1) meant the real repo manifest was being read instead of this broken one. Fixed by balancing the braces (verified by round-tripping through `clojure.edn/read-string`).
3. **No real Clojure source for the fixture's `:factory` symbols.** `marigold.bridge/create-module` and `marigold.bridge.comm/create-comm-node!` were referenced but never backed by real `.clj` files -- again invisible while issue (1) was silently substituting the repo's real, working `modules/marigold.bridge/src/...`. `config get`/`config unset` don't need full module activation and so didn't notice; `config set` does (to reconcile/register the berth), and failed with the entire CLI command table empty ("Unknown command: config") once the id collision was fixed and the real backing module was no longer being substituted. Fixed by adding matching `src/marigold/cgxa/bridge.clj`, `src/marigold/cgxa/bridge/comm.clj`, `src/marigold/cgxa/longwave.clj` to the Background (mirroring the real fixture's own shape) and adding `"src"` to each module's `deps.edn` `:paths`.
4. **`:helm/outer`'s declared shape didn't match what the scenario writes.** It was declared as an entity-table (`{:type :map :value-spec {:type :map}}` -- i.e. "each entry under `:helm/outer` is itself a map, keyed by an absorbed id"), but the scenario sets a scalar leaf (`relays.helm-station.helm/outer.inner/key x`, value `"x"`) -- a schema-legitimate mismatch (coercing `"x"` to `:map` correctly failed). Changed `:value-spec` to `{:type :string}` so `:helm/outer` is a map of namespaced-key -> string, matching the scenario's own intent (and the bean's real-world motivating shape, e.g. `gchat/spaces.spaces/AAQA...respond`).
5. Separately (not stacked on the above): the `get` and `unset` scenarios' own `Given the isaac file "isaac.edn" exists with:` steps overwrote the Background's `isaac.edn`, dropping the `:modules` declaration. Since `:relays` is only a recognized/loadable config table when a module declares its berth, `config get` legitimately returned "not found" (the loader doesn't surface config for a table no installed module owns) even though the raw file had the right data. Fixed by including `:modules` in both scenarios' own `Given` blocks.

Also fixed the Background's root step: it used `Given an empty Isaac state directory "/tmp/cgxa"`, which is *always* virtual/mem-fs regardless of path -- incompatible with a scenario that needs `borkdude.deps` (a real subprocess) to build a classpath from real `deps.edn`/`.clj` files. Switched to `Given an empty Isaac root at "/tmp/cgxa"`, which resolves to real-fs for an absolute non-`/test` path (see `empty-state`'s `virtual?` heuristic in `spec-support/src/isaac/foundation/root_steps.clj`) -- matching how `features/cli/config_resolution.feature` (a working example with real local/root modules) is written.

**What I could not do / left open:** the bean's fourth stated scenario -- "a set creating an unknown key under a schema'd map is refused, not written" -- is **not** implemented as a feature scenario, and `mutate_spec.clj`'s existing unit example ("refuses a set that creates an unknown key inside a schema'd map") still asserts *today's* behavior (`:ok` + an `unknown key` warning), not a hard refusal. This is the same open question the prior checkpoint flagged: making an unknown key under a schema'd map a hard block (rather than a warned-through write) is a `mutate/set-config` blocking-errors *policy* change with effects far beyond namespaced keys -- every existing "warn and write anyway" path would need re-examining. I judged that out of scope for "the grammar treats `/` as part of the key" and left it for the planner, per the prior checkpoint's own flag, rather than unilaterally changing blocking-error policy.
