Model agent orchestration as explicit state machines (idea via Micah's dad; see slagyr/statemachine — transition tables, Mealy actions, superstates). Today's orchestration is an implicit FSM smeared across skills, band config, cron, and humans; its failures this week were lost-event bugs (orphaned claim = state with no action fired; silent turn death = state no transition exits; continuation-budget hold = manual timeout). DESIGN: (1) Per-orchestration TRANSITION TABLE, actions are prompts (Mealy); superstates for shared transitions (e.g. any-state budget-timeout -> held/notify-human). New project = one table + crew/workspace bindings, replacing the file/crew/session frenzy. (2) Two machine archetypes: per-entity instances (one per bean) for singular steps; SINGLETON ACCUMULATOR machines for collected steps (hardening): collect action appends to basket, guarded drain transition (count >= N / quiescence via cron tick / explicit), action = ONE prompt carrying the basket. (3) STATE-STORE PORT: instances = entity-id -> state + context. Beans are the default adapter (git-backed, auditable, human-EDITABLE — a human flipping status is a manual transition; re-hail is event injection); file/EDN adapter for orchestrations without repos; in-memory for ephemeral fan-outs. Usable entirely without beans. (4) EVENTS, two kinds, no new messaging scheme: SEMANTIC DECLARATIONS via a crew-side `signal` tool (signal :landed {:bean .. :commit ..}) writing event records the foreman consumes — replaces remembered hail choreography with one structured tool call, routing owned by config; INFRASTRUCTURE OBSERVATIONS emitted by the system (turn ended/died via isaac-e04k, workspace freed, commit observed) serving as BACKSTOP transitions: 'turn ended in :claimed with no signal' is itself an event the table handles (nudge/re-dispatch/escalate). The model indicates when it finishes; the machine notices when it doesn't. (5) ACTIONS ride hail unchanged (durable, deferred, attention). Composition: foreman decides WHAT, dispatch-gate/workspace module decides WHERE, hail carries, cron ticks, hooks route. New module — NOT hail (hail stays pure messaging; three-time ruling this week). Name note: 'isaac-foreman' was hallucinated into scrapper's gists by grok-4.20 two days before this design existed — confabulation as prophecy. ## Addendum (2026-08-22, Micah): external event triggering

Events must be triggerable externally -> CORRECTED (2026-08-22, Micah's catch): hooks' essence is webhook -> prompt -> TURN; foreman events are non-turn, so reusing hooks would change what hooks is. Instead the foreman contributes its OWN route through the isaac-server route berth (the same extension point hooks and cli-server use — server owns HTTP): `POST /foreman/events` behind the server's existing token auth. Hooks unchanged, remains the webhook-means-wake-a-crew module (pinky telemetry untouched). Migration example: a CI webhook targets the event route and the TABLE decides whether any prompt fires. **Two doors, one intake**: the crew-side `signal` tool and the external endpoint write the same event envelope to the same durable queue. Durability rule (hails-never-die for events): persist-before-ack — append to disk, then 200; the machine consumes from disk, so an accepted event fires even across restarts. Unlocked table inputs: GitHub Actions posting :ci-passed (CI as first-class transition, not a report a crew reads), human curl for manual events, remote cron ticks, cross-host isaac signaling.


## Addendum (2026-08-22, Micah): observability + CLI

The machine's state IS the answer to "where is this bean?" — currently answered by digging logs/transcripts (the planner spent this week doing exactly that: ssh + jsonl tails + hail-dir greps for every status question; qxvl's stall took forensic reconstruction). Surface:
- **Read endpoints** beside the event route: GET /foreman/instances/<id> -> {state, since, last-event, pending-action, accumulator basket}; GET /foreman/instances?state=held ("what needs a human" as a query). The persisted event intake doubles as an append-only TRANSITION LOG per instance — audit trail/"how it got here" for free.
- **CLI**: `isaac foreman status <id>`, `isaac foreman list --state held`, `isaac foreman history <id>` — rides the endpoints, so it works remotely via cli-proxy (no ssh archaeology).
- **`isaac foreman signal <id> <event>`** — the HUMAN door for manual event injection (today: edit bean status + re-hail by hand), first-class and logged like any event. Three doors, one intake: crew tool, external endpoint, CLI.


## Addendum (2026-08-22, Micah): hail trajectory under the foreman

Micah observed hail bands are near-redundant with webhooks (both: config-bound prompt -> turn; hail adds queueing + target flexibility). Resolution: the redundancy is FUTURE, created by the foreman itself. Today hail is distinct (no HTTP needed — file-based, works serverless; hails-never-die apparatus: deferral, retry, attention, dead-letter, reply_to threading). But bands/reach/reply-to exist for PEER choreography without an orchestrator — exactly what the foreman absorbs (routing -> tables, threading -> transition history, worker-to-worker hails -> signals). Trajectory, by disuse not surgery: **hail contracts toward its irreducible core — a durable turn-request queue** ("start a turn on this target with this prompt, durably, when free"); webhooks/cron/foreman-actions/CLI become different doors into that one queue. Keep hail untouched now; let peer choreography retire naturally.
